# Decisions

One line per decision: X over Y because...

- arm64 Lambda + ubuntu-24.04-arm runners over amd64 because my Mac is Apple Silicon: native builds everywhere, ~20% cheaper Lambda, no emulation. Trade-off: repo must stay public for free ARM runners.
- aws login (IAM user, console creds -> 15-min rotating creds) over IAM Identity Center because Identity Center requires AWS Organizations, which force-upgrades a Free plan account to Paid and voids the $100 credit. Same outcome: zero long-lived keys on my laptop.
- venv + pinned requirements.txt over Poetry/uv because fewer moving parts, the Lambda image installs requirements.txt directly, and Trivy scans pinned versions.
- pip-tools compiled lockfiles over direct-only pins because Trivy fs only sees versions written in requirements.txt, so transitive CVEs (e.g. starlette) would be invisible; hashes deferred to keep Day 1 simple.
- Multi-stage build with `pip install --target` over a single-stage image because only runtime deps (requirements.txt) land in the final image; dev tools and pip cache never ship.
- Base image pinned by multi-arch index digest over the floating :3.12 tag because rebuilds are reproducible and Trivy results are attributable to a known base; trade-off: we must bump the digest to receive AWS base patches.
- `USER 1000` in the prod stage over leaving root because Trivy flags root images (DS002) and least privilege is the right default. Verified: Lambda docs say it runs functions as "a default Linux user with least-privileged permissions" and that "you don't need to specify a USER in your Dockerfile", but the files must be readable by that user (https://docs.aws.amazon.com/lambda/latest/dg/images-create.html). Unverified: whether Lambda honours or ignores the Dockerfile USER at runtime; the docs don't say, so USER here mainly affects local runs.
- Strip RIE from the prod image over ignoring its CVE because real Lambda never runs it; scan exactly what we ship.
- `dnf upgrade --releasever=<exact AL2023 release>` in the image over shipping the AWS base as-is because the pinned base had 43 HIGH OS CVEs (curl, libcap, openssl, pcre2, rpm) already fixed in a later AL2023 release (2023.12.20261026 -> 0 HIGH; 2023.12.20261021 still left 13). Trade-off: we diverge from AWS's exact tested base and the image is ~11.7 MB bigger (inspect.Size), but it is patched and reproducible because the release version is pinned, not "latest". AL2023 repos are version-locked, so a plain upgrade patches nothing; trade-off: AL2023_RELEASE must be bumped manually.
- Trivy CLI tarball + hardcoded sha256 over aquasecurity/trivy-action because the action's tags were force-pushed to malware (GHSA-69fq-xp46-6x23, 2026-03-19); verifying the binary hash removes trust in mutable tags.
- Branch protection with required lint/test/security checks and enforce_admins=true over admin bypass because the "bad code can't reach main" claim must hold even for me; emergency path is temporarily disabling protection.
- Local state for bootstrap/ only (gitignored) over a remote backend because the state bucket can't store the state of its own creation; trade-off: if the laptop copy is lost, re-`terraform import` the bucket (prevent_destroy guards against accidental deletion). infra/ uses the S3 backend.
- SSE-S3 (AES256) over a customer-managed KMS key for the state bucket because a CMK costs $1/key-month + $0.03/10k requests (AWS Pricing API, ap-southeast-1) and this bucket's risk is covered by IAM, TLS-only policy, and block-public-access; trade-off: no separate key policy or key-level audit trail.
- State bucket named `guarded-deploy-tfstate-<account-id>` via `aws_caller_identity` over a hardcoded name because S3 names are global and the account ID stays out of the public repo's code.
- AWS provider `~> 6.74.0` + committed `.terraform.lock.hcl` (hashes for darwin_arm64, linux_arm64, linux_amd64) over a loose `>= 6.0` because patch-only upgrades and checksum-verified providers make plans reproducible on laptop and CI.
- Expire noncurrent state versions after 90 days over keeping them forever because versioning is for recovering recent bad writes and unbounded versions slowly cost money.
- No S3 server access logging on the state bucket (Trivy AWS-0089, LOW) over a separate log bucket because it adds a second bucket (which itself would need logging) for a single-user project; revisit if more people get access.
- Partial S3 backend config (bucket passed via `-backend-config` from bootstrap output) over a hardcoded bucket name because it keeps the account ID out of the public repo's code, consistent with bootstrap/.
- `terraform plan -lock=false` for reviews before apply is approved over default locking because `use_lockfile` PUTs a `.tflock` object to S3 (an AWS write); applies always lock.
- Inline `#trivy:ignore:<ID>:exp:2027-04-23` next to each paid-KMS finding (AWS-0132, AWS-0033, AWS-0025, AWS-0017) over a central .trivyignore because the justification lives next to the code it excuses and works for any scan root; expiry = Free plan credit expiry.
- ECR repository policy letting lambda.amazonaws.com pull (scoped by aws:sourceArn to this function) over granting the deploy role ecr:SetRepositoryPolicy because AWS docs say one side is enough for same-account, and otherwise Lambda tries to edit the repo policy itself using the caller's permissions.
- API Gateway stage throttling (burst 10, rate 5) as the cost guard over Lambda reserved concurrency because the account limit is 10 (`aws lambda get-account-settings`) and Lambda must keep 10 unreserved, so reserving any is not possible.
- OIDC provider without thumbprint_list over pinning a thumbprint because IAM validates GitHub's issuer against trusted root CAs and the attribute is optional in provider 6.74.0 (`terraform providers schema`); a pinned thumbprint goes stale on cert rotation.
- Image ENV as the single source of truth for GIT_SHA over also setting it in the Lambda environment because /health must report the SHA actually running; a config value could shadow it (precedence not stated in AWS docs) and go stale, since the deploy role cannot update function config.
- First image pushed from the laptop as a one-time bootstrap (phased apply: ECR via -target, push, full apply) over a separate ECR root module because it's a one-off; every later image comes from CD. Guard: built from a CI-green commit, full 40-char SHA tag, --provenance=false --sbom=false, trivy image HIGH/CRITICAL exit 0 before push.
- Terraform applied from the laptop only, CD never runs it, over a CD-driven terraform apply because the deploy role then needs no state-bucket, IAM, or broad read permissions; CD only pushes images, publishes versions, and moves the alias. CD jobs don't use a GitHub `environment:` because it changes the OIDC sub claim the trust policy pins.
- DynamoDB point-in-time recovery on (Trivy AWS-0024) over off because it costs $0.228/GB-month of table size (Pricing API), ~$0 here, and protects against bad writes.
- HTTP API stage access logging to its own 7-day log group (Trivy AWS-0001) with a minimal JSON format over no logs because per-request status/latency/integration errors are needed to debug failed smoke tests. No account-level API Gateway CloudWatch role: the HTTP API logging docs don't list it (it's on the REST API logging page); verified at apply: access logs delivered while `aws apigateway get-account` showed cloudwatchRoleArn null.
- X-Ray off, Trivy AWS-0066 suppressed inline (exp 2027-04-23), over enabling tracing because I couldn't confirm it's free on this Free plan and one function + one table is debuggable from logs.
- Two health gates (pre-traffic `aws lambda invoke --qualifier NEW` with an HTTP API v2 `GET /health` event, then post-traffic `curl <api_url>/health` after the alias move) over a single post-deploy check because the direct invoke catches a broken build before any user sees it, and the public check catches what direct invoke can't (API route, alias permission, integration). Both require status 200 AND `version == GIT_SHA`. The smoke event lives in `scripts/events/health.json` and a pytest feeds it to the real Mangum handler so it can't drift.
- Auto-rollback depth = exactly 1 (alias back to PREV, then `get-alias` must equal PREV) over "last known good" search because PREV is the only version proven to serve traffic most recently. Manual rollback max safe depth = 9 versions back (was 4 with keep-last-5): the ECR lifecycle keeps the 10 newest images by `pushed_at_time` (https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html), and a function whose image is deleted from ECR enters `Failed` (https://docs.aws.amazon.com/lambda/latest/dg/images-create.html) or `Inactive` (https://docs.aws.amazon.com/lambda/latest/dg/functions-states.html; the two pages disagree) and invocations fail. Reason code `ImageDeleted` (https://docs.aws.amazon.com/lambda/latest/api/API_FunctionConfiguration.html). Images pushed by failed deploys also use up slots, so the depth only holds if every push went live.
- `workflow_dispatch` boolean `inject_live_check_failure` (default false; always false on push) over a deliberately broken commit because it proves the real rollback path on a healthy build without shipping bad code; the script logs FAULT_INJECTION loudly and the run still goes red.
- CD `concurrency: cd-main` with `cancel-in-progress: false` over CI-style cancellation because cancelling between "alias moved" and "live check" would leave unverified code live with no rollback; later pushes queue instead.
- aws CLI for ECR login, image lookup, and every Lambda call over third-party actions (amazon-ecr-login etc.) because fewer dependencies run with deploy credentials. The one action kept is AWS's own `aws-actions/configure-aws-credentials` (pinned v6.3.0 by SHA; no repo or global advisories via `gh api`) for the OIDC exchange and credential masking; v6.3.0 over v6.3.1 (released 2026-11-25, a proxy-only fix we don't need) for soak time.
- `function-updated-v2` / `function-active-v2` waiters over `function-updated` / `published-version-active` because `aws lambda wait help` (CLI 2.38.5) says the v2 waiters poll GetFunction (allowed for the deploy role) while the others poll GetFunctionConfiguration (not granted); adding an IAM action would need a terraform apply.
- Deploy role ARN as a repo **secret** and API URL as a repo variable over hardcoding (or both as variables, the original choice) because the ARN contains the account ID and `configure-aws-credentials` echoes its inputs before `mask-aws-account-id` takes effect; only secrets print as `***`. This leaked in the first CD run's public log (run deleted, see docs/incidents.md). The API URL is public by design. `::add-mask::` still covers the account ID in later steps.
- Same-SHA re-run short-circuits twice (live already runs IMAGE_URI → exit 0; NEW == PREV → exit 0) and CD skips build/push when `describe-images` finds the tag, over failing on the immutable tag, because re-running a deploy must be safe; only `ImageNotFoundException` triggers a build, other errors fail.
- ECR keep-last-10 over keep-last-5 because lifecycle expiry counts every pushed image, including ones whose deploy failed: 5 failed experiments in a row would have expired the image `live` still runs, breaking production. 10 leaves room for the Day 3 experiments, and manual rollback depth becomes 9 (assuming every pushed image went live). Cost: `imageSizeInBytes` = 228304212 (`aws ecr describe-images`) × 10 images ≈ 2.28 GB upper bound (no layer sharing assumed) × $0.10/GB-month (Pricing API, APS1-TimedStorage-ByteHrs) ≈ $0.23/month; the extra 5 images ≈ $0.11/month. Still not a guarantee: a rule that never expires the image `live` points to is in CLAUDE.md Next steps. Terraform replaces (not updates) `aws_ecr_lifecycle_policy` on any policy change (`-/+ … forces replacement` in plan); nothing can expire in that window because no policy exists then.
- OIDC trust policy pinned to GitHub's immutable subject (`repo:Zeeqie@260482962/guarded-deploy@1431477050:ref:refs/heads/main`, exactly as seen in CloudTrail) over disabling `use_immutable_subject` because the numeric owner/repo IDs mean a deleted-and-re-created repo with the same name can't assume the role; disabling it would also have been a repo-settings change. Found when the first CD run failed closed (docs/incidents.md).
